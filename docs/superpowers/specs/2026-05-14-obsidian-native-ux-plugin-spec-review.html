공식 문서 근거

spec 작성 전에 확인한 내용
출처 확인한 근거 Spec 반영
Build a plugin plugin 개발은 TypeScript를 사용하며 main vault 밖에서 테스트하는 흐름을 권장한다. Spec은 disposable vault 개발과 smoke test를 요구한다.
Vault API Vault.process()는 read/write 사이의 데이터 손실 위험을 줄이기 때문에 content 기반 수정에 적합하다. Spec은 plugin의 직접 fs write를 거부하고 ObsidianVaultPort를 도입한다.
Obsidian API README plugin은 App, Vault, Workspace, MetadataCache에 접근할 수 있고, Plugin은 command, ribbon icon, settings tab, plugin data를 지원한다. Spec은 command palette, ribbon, settings, metadata-cache-as-helper-only 경계를 포함한다.
Sample Plugin 공식 template은 manifest.json, main.ts, esbuild, Modal, Notice, settings tab 예제를 사용한다. Spec은 이 구조를 따르는 packages/obsidian-plugin scaffold를 제안한다.
Obsidian CLI CLI는 plugin command 목록/실행, plugin reload, screenshot capture, developer error 확인에 사용할 수 있다. Spec은 Obsidian CLI를 product UX 의존성이 아니라 E2E harness로만 사용한다.

스펙 리뷰 결과

blocker와 후속 주의사항

blocker 없음: UX 방향

Spec은 task 생성, normalize, move preview, apply를 Obsidian 안에서 수행하도록 정한다. CLI는 fallback/debug 용도로 남긴다.

blocker 없음: source of truth

Spec은 Phase 2 규칙을 유지한다. issue frontmatter가 authoritative source이고, board file은 generated projection 및 pending proposal input이다.

blocker 없음: adapter boundary

Spec은 CLI shell-out을 피하고 VaultPort 경계를 추가해 CLI와 plugin이 core logic을 중복 없이 공유하게 한다.

해결됨: desktop only

Phase 3은 Mobile Obsidian을 의도적으로 제외한다. 구현 계획은 desktop Obsidian과 desktop GUI E2E를 대상으로 해야 한다.

해결됨: explicit raw promotion

Raw Kanban card는 Phase 3에서 명시적 command와 confirmation modal을 통해서만 승격한다. 자동 promotion은 거부한다.

해결됨: board 유지

New Task 이후 사용자는 기본적으로 board에 머무른다. 생성된 issue를 여는 동작은 action 또는 setting으로 둔다.

해결됨: install evidence

local dev 속도를 위해 symlink install은 허용하지만, 공식 smoke/E2E 증거는 copy-installed plugin artifact를 사용해야 한다.

해결됨: safe ribbon entry

모든 command는 Command Palette에서 사용할 수 있다. 기본 ribbon icon 하나는 menu/status panel만 열고 직접 write를 apply하지 않는다.
